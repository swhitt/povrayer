how it actually loads & runs

From a cold GitHub Pages hit to ray-traced pixels in your tab

Every request, every header, every worker, and every byte that crosses the JS ↔ wasm boundary, start to finish. POV-Ray 3.8 is a 30-year-old C++ ray tracer; this is the machinery that makes it run, multi-threaded, inside a static page with no server.

live at povrayer.com · static files only · no backend · ~3.9 MB wasm

TL;DR

The whole thing in one breath

Five moves. The hard part isn't ray tracing. It's that a wasm ray tracer needs real threads, real threads need SharedArrayBuffer, and that needs HTTP headers a static host won't send. Everything in Act 1 exists to win that fight.

/work/out.png → fresh Uint8Array → Blob → object URL → <img>. Instance torn down. Repeat.
The one architectural fact that explains everything else: POV-Ray uses pthreads for multi-core rendering. In wasm, a pthread is a Web Worker sharing one WebAssembly.Memory({ shared: true }). A shared memory buffer is only handed to JS when the page is cross-origin isolated, which requires two response headers GitHub Pages flatly refuses to send. Act 1 is the workaround.
ACT 1

Opening the page on GitHub Pages

What gets requested, in what order, and the header sleight-of-hand that turns a header-less static host into a cross-origin-isolated context.

The deploy layout: everything is flat

CI builds the wasm in Docker, then the Pages job copies dist/* and web/* into one directory and publishes it under the /povrayer/ subpath. Flat on purpose: every URL in the page is relative (./ui.js, ./index.js, ./povray.wasm), so the wrapper's ./index.js resolves right next to povray.mjs and the editor scripts. 

# .github/workflows/pages.yml, gated on a green CI run
mkdir -p _site
cp -R dist/* _site/   # index.js, povray.mjs, povray.wasm (the engine)
cp -R web/*  _site/   # index.html, ui.js, coi-serviceworker.js, styles...

On every later visit the service worker is already installed, so there's no reload step. The first /povrayer/ response is already isolated and the page is interactive immediately.

Why the service worker exists at all

To hand JS a SharedArrayBuffer, a browser demands the page be cross-origin isolated, which means the top document was served with:

Response header Value Why
Cross-Origin-Opener-Policy same-origin Severs the window from cross-origin openers (no shared browsing-context group).
Cross-Origin-Embedder-Policy require-corp Every subresource must opt in to being embedded. Together with COOP this flips crossOriginIsolated → true.
Cross-Origin-Resource-Policy cross-origin Stamped on every subresource so require-corp accepts them.

GitHub Pages lets you set zero custom headers. The fix is a classic: a service worker that re-fetches every response and rewrites the headers locally before they reach the page. It's loaded synchronously in <head>, before anything else, so it controls the page as early as possible. 

// coi-serviceworker.js: the fetch handler, per response
newHeaders.set("Cross-Origin-Embedder-Policy", "require-corp");
newHeaders.set("Cross-Origin-Resource-Policy", "cross-origin");
newHeaders.set("Cross-Origin-Opener-Policy",   "same-origin");
return new Response(response.body, { /* ...with newHeaders */ });

web/coi-serviceworker.js:43

Local patch worth knowing: upstream coi-serviceworker sends COEP: credentialless on non-Chromium browsers. Safari (desktop + iOS) doesn't support credentialless, so the page would never isolate and the engine would never start. This fork forces require-corp everywhere (safe here because every asset is same-origin and the SW also stamps CORP: cross-origin).

The first-visit reload dance

A freshly-installed SW doesn't control the page that installed it. So on a cold visit the page loads without the headers, notices it isn't isolated, and reloads once so the now-active SW can intercept. The page itself double-checks and shows a banner if it's still not isolated: 

if (crossOriginIsolated) {
  sessionStorage.removeItem('coi-retry');   // good, engine can run
} else {
  isoWarning.hidden = false;                // "SharedArrayBuffer unavailable…"
  // reload as soon as the SW takes control; sessionStorage guards an infinite loop
  if (navigator.serviceWorker?.controller) coiRetry();
  else navigator.serviceWorker?.addEventListener('controllerchange', coiRetry);
}

PRIMER

How Emscripten works (the general picture)

Before Act 2 makes sense, here's what Emscripten actually produces and how a C++ main() ends up callable from JavaScript. If you know this cold, skip to Act 2.

It's a compiler toolchain, not a runtime

Emscripten is LLVM/Clang with a wasm backend plus a pile of JS “glue.” You point it at C/C++ (here: the POV-Ray 3.8 source) and it emits three kinds of output:

📦
povray.wasm, the compiled binary
POV-Ray's C++ translated to WebAssembly instructions. ~3.9 MB. Pure computation: it can't touch the DOM, the network, or files on its own.
🔌
povray.mjs, the JS glue / loader
Fetches & instantiates the wasm, wires up imports, emulates a libc/OS (files, time, stdout), manages the pthread worker pool. The part you actually call.
🧵
Worker glue (here: the same .mjs, re-imported)
Each pthread is a Web Worker running the same module in a special "I am a pthread" mode, sharing one memory with the main instance.

The bridge: linear memory + an imports/exports table

A wasm module has one big ArrayBuffer of linear memory and a list of functions it exports (callable from JS) and imports (JS functions it calls out to). C pointers are just integer offsets into that buffer. So when JS wants to give the program a string, it writes the bytes into linear memory and passes the offset; when the program prints, it calls an imported JS function with a pointer + length that JS reads back out. Emscripten generates both sides of every one of those calls.

exports → callMain, malloc, FS helpers… imports → print, printErr, syscalls, now() memory → one shared ArrayBuffer, pointers = offsets

Faking an operating system in the browser

POV-Ray is a command-line program. It opens files, reads argv, writes a PNG, prints progress. None of that exists in a tab, so Emscripten emulates it:

POV-Ray expects… Emscripten provides…
a filesystem (fopen, fread) MEMFS, an in-memory virtual FS. FS.writeFile("/work/scene.pov", …) from JS makes a "file" the C code can open as if it were on disk.
argc / argv callMain(["+I/work/scene.pov", "+W512", …]): JS hands the CLI args straight to main().
stdout / stderr Imported print / printErr callbacks. Every line POV-Ray writes surfaces as a JS string.
exit(code) An onExit(code) callback. With EXIT_RUNTIME the whole instance tears down cleanly when main() returns.
threads (pthreads) Web Workers + one shared: true memory. pthread_create → spin up / reuse a worker.

Threads are the whole reason this is hard

Native pthreads share one address space. Emscripten reproduces that by giving every worker the same WebAssembly.Memory instance, but JS only allows a memory's backing buffer to be shared across workers when it's a SharedArrayBuffer, which (full circle) only exists under cross-origin isolation. That's the thread that ties Act 1 to everything below.

Two Emscripten flags this build leans on:
PROXY_TO_PTHREAD: main() runs on a worker, not the page thread, so the UI never freezes during a multi-second trace. callMain() returns immediately; completion arrives via onExit.
EXIT_RUNTIME=1: when main() returns the runtime is fully torn down (memory, workers, MEMFS gone). The wrapper uses this to get a pristine instance per render instead of reusing dirty state.

The lifecycle, generically

  1. Instantiate
    WebAssembly.instantiate(bytes, imports) compiles the binary and links it to the JS-provided imports + memory. Emscripten wraps this in a factory function the glue exports.
  2. Set up the environment
    MEMFS mounted, argv prepared, stdout hooks attached, the pthread worker pool pre-warmed.
  3. Stage inputs
    JS writes files into MEMFS and assembles the argv array, the program's whole view of the "outside world."
  4. Run
    callMain(argv) invokes the exported main(). Work fans out across worker threads over shared memory.
  5. Collect & tear down
    JS reads output files back out of MEMFS, then the runtime exits. Outputs must be copied out, because the memory is about to vanish.
ACT 2

Booting the wasm wrapper

How povrayer's thin TypeScript wrapper turns that generic Emscripten module into a clean render(source, opts) → PNG bytes promise, and why it's loaded so late.

Exactly one module touches wasm

The page code never imports the engine directly. render-client.js is the single chokepoint; it imports ./index.js (the built wrapper), which is the only thing that knows povray.mjs exists. Everything funnels through one busy flag so a still render and an animation can never run at once. 

// web/render-client.js: the only wasm import in the app
import { render, renderAnimation, PovrayError } from './index.js';

Lazy, cached factory: fresh instance per render

The 3.9 MB wasm isn't fetched until your first render. The wrapper dynamically imports povray.mjs once and caches the factory (which holds the compiled bytes), but spins up a brand-new instance for every render. EXIT_RUNTIME makes that cheap and clean: FS, memory, and worker state never leak between renders. 

function loadFactory() {
  if (!factoryPromise) {
    factoryPromise = import("./povray.mjs").then((m) => m.default);
  }
  return factoryPromise;   // compiled wasm cached; ~100-300ms per instance is noise vs a multi-second trace
}

What povray.mjs does the instant it's imported

  1. Sniff the environment
    Same file runs in Node and the browser. It checks globalThis.window / WorkerGlobalScope to decide between worker_threads and Web Worker, and whether it is the main thread or a pthread (name === "em-pthread").
  2. Locate the binary relative to itself
    new URL("povray.wasm", import.meta.url), resolved next to the glue, which is why the flat deploy layout matters.
  3. Allocate shared memory
    new WebAssembly.Memory({ initial, maximum: 32768, shared: true }): a 2 GB shared ceiling (32768 × 64 KB pages). shared:true is the payoff for all of Act 1.
  4. Compile & instantiate
    WebAssembly.instantiate links the binary to that memory and the JS imports (print, syscalls, …).
  5. Spawn the pthread pool
    One Web Worker per render thread, each re-importing the same module in pthread mode over the shared memory. 
// the pthread worker spawn, straight out of the emscripten glue
worker = new Worker(
  new URL("povray.mjs", import.meta.url),
  { type: "module", workerData: "em-pthread", name: "em-pthread" }
);
Never run this through a bundler. The worker is spawned via new URL("povray.mjs", import.meta.url) and ignores Emscripten's locateFile hook (emscripten #22508). povray.mjs and povray.wasm must be served as opaque static assets exactly where the glue expects them. Bundle or rename them and the threads silently fail to spawn.

Thread count

Threads default to navigator.hardwareConcurrency clamped to 1–32, overridable in the UI. It becomes POV-Ray's +WT flag. More workers, more cores chewing the shared framebuffer.

The adaptive debounce (so it doesn't melt your laptop)

Live draft doesn't render on every keystroke. It waits, and the wait scales with how long the last draft took: a heavy scene backs off, a trivial one fires near the floor.

floor 250 ms ceiling 2000 ms delay ≈ lastDraftMs × 0.75 draft res capped to 320 px longest edge antialias off for drafts

When the timer fires it re-reads the newest text (so a burst of keystrokes collapses to a single render of the final text), checks the scene looks syntactically settled, and bails if it isn't isolated or the engine is busy. A newer edit mid-render abort()s the in-flight draft and supersedes it.

Getting the pixels back out, carefully

The output is copied into a fresh, non-shared buffer before the instance dies. This is the single most important rule in the wrapper:

Never hand callers a view into wasm memory. With ALLOW_MEMORY_GROWTH on a shared memory, the underlying buffer is replaced when it grows, so any cached HEAPU8 view would suddenly read garbage. The wrapper never touches the heap directly: FS.writeFile / FS.readFile plus an explicit Uint8Array.from(...) copy are the only data paths in and out.

From there render-client.js wraps the bytes in a Blob, mints an object URL, and the UI swaps it into <img id="output">. A draft success is the only thing that swaps the image; a draft error keeps the last good frame and whispers the message inline (a polite live region, not an alert on every keystroke).

Cancel = terminate the threads

Hit Stop / Esc and the AbortController fires PThread.terminateAllThreads(). Violent by design: the instance is thrown away after every render anyway, so killing it mid-trace is safe; the next render starts from a fresh one and rejects the current promise with an AbortError.

Live draft

Auto-fires on idle. ≤320 px, AA off, no progress bar, no log. Superseded by newer text. Keeps the last good image on error.

Explicit render

Ctrl/Cmd+Enter or the button. Full res + AA, drives the progress bar & log, and always wins: it aborts a running draft first (pendingFull).
